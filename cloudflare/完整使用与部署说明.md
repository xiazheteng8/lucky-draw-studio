## 1. 部署方案与访问入口

| 方案 | 运行位置 | 数据位置 | 适合情况 |
| --- | --- | --- | --- |
| Windows 本地 | 本机 Node.js | 项目 `data/` | 自己电脑演示、现场大屏、离线名单抽奖 |
| VPS Node.js／Docker | 服务器进程／容器 | `DATA_DIR` 或 Docker 卷 | 自己管理域名、HTTPS、磁盘和备份 |
| 独立 Cloudflare Worker | Worker + Static Assets | Durable Objects、KV、R2 | 一个站点完成前端和 API |
| Cloudflare Pages + Worker | Pages 静态页面 + Functions 代理 + 独立 Worker | 仍在 Worker 的 DO／KV／R2 | 希望 Pages 承载页面、GitHub Actions 自动发布 |

Cloudflare Pages 方案中，页面真实部署在 Pages，浏览器向同源 `/api/...` 请求，Pages Functions 使用名为 `API_BACKEND` 的 Service Binding 调用独立 Worker。Pages 不连接你的电脑或 VPS。Worker 负责账号、权限、定时开奖、数据和上传媒体。

纯静态托管只有 HTML／CSS／JS，无法单独提供账号会话、数据库、验证码、OAuth 回调、定时开奖或存储。原生 GitHub Pages 不能运行本项目的 Pages Functions；不要把 GitHub Pages 和 Cloudflare Pages 混为一谈。GitHub 在这里负责代码与 Actions，实际站点发布到 Cloudflare。

| 地址 | 用途 | 访问权限 |
| --- | --- | --- |
| `/` | 公开创建表单、工作空间 | 可打开表单，提交创建与管理需登录 |
| `/admin` | 活动管理控制台 | 操作需登录，管理自己的活动 |
| `/account`，兼容 `/login` | 登录、注册、邮箱／手机绑定 | 公开账号入口 |
| `/setup` | 第一次设置站长 | 需要私有初始化密钥；成功后关闭初始化 |
| `/owner` | 站长登录方式配置、用户列表 | 仅站长 |
| `/settings/wechat` | 活动微信签到设置入口 | 仅站长操作配置 |
| `/settings/dingtalk` | 活动钉钉签到设置入口 | 同上 |
| `/settings/telegram` | 活动 TG 签到设置入口 | 同上 |
| `/live.html?id=活动编号&token=大屏令牌` | 分享大屏 | 按活动令牌访问 |
| `/interact.html`、`/join.html` | 手机签到／互动 | 使用管理页面生成的完整链接 |
| `/export.html` | 结果图片、动画回放、现场录像导出 | 按页面实际会话与活动权限验证 |

旧的 `/live/编号`、`/overlay/编号` 等兼容入口仍可用于已有链接，但应直接复制活动卡片提供的完整地址，保留其查询参数。不能把大屏令牌当成站长密码或账号登录凭据。需要私有管理权限的结果和表格接口仍要求所有者／站长会话。

## 2. 第一次启动与站长初始化

### 2.1 初始化顺序

1. 先部署运行服务、设置私有 `SETUP_KEY`（Cloudflare 必须），再访问 `/setup`。
2. 本地／VPS 未指定 `SETUP_KEY` 时，程序会生成一次性密钥，写入私有数据目录 `owner-setup-key`，并在首次启动日志中显示。只在自己的服务器终端读取，不把日志原样公开。
3. 在同一个浏览器打开 `http://localhost:3000/setup` 或 `https://lucky.example.com/setup`，输入初始化密钥、站长用户名、密码和重复密码。
4. 用户名为 3–64 位，可用文字、数字、下划线、`@`、`.`、`-`；密码至少 10 位。建议在浏览器表单允许长度内使用独立随机密码。
5. 成功后进入 `/owner`。再刷新 `/setup`，应不再允许创建第二个站长。

Cloudflare 的 `SETUP_KEY` 是服务端 Secret，不是浏览器脚本变量，也不是站长密码。生成一段足够长的随机值，在 Cloudflare 控制台 Worker → Settings → Variables and Secrets 添加 Secret，或执行 `npx wrangler secret put SETUP_KEY` 并在交互中输入。不要把值写进 `wrangler.jsonc`、`.github/workflows`、`public/` 或公开压缩包。

初始化完成会把升级前没有归属的旧活动交给站长；用户后续新建的活动分别归自己的账号。站长能管理全部活动，普通用户不能通过更换活动编号查看或操作其他人的私有活动。旧活动的数据保留规则与新注册临时用户不同，升级时不会把旧活动直接当成到期临时活动删除。

### 2.2 日常登录

普通用户在 `/account` 注册或登录。注册表单需要确认活动到期清理规则。关闭某种登录方式或凭证不完整时，该外部入口不会成为可用登录方式。站长专用密码入口为 `/account?owner=1&next=%2Fowner`，用于在普通密码注册停用后继续进入站长后台。

用户名密码注册默认属于未验证用户。默认限制为：新活动应在创建后 24 小时内开奖；未开奖超过期限会清理；已开奖活动从揭晓结束起保留 24 小时，包含手动逐位揭晓的进度延长。到期清理包括活动、评论、中奖与互动数据。邮箱／手机验证绑定、第三方真实授权可产生已验证身份；绑定后新活动采用新身份规则，旧活动不应假定自动取消原到期时间。以活动创建时保存的规则为准。

## 3. Windows 本地运行

### 3.1 双击启动

1. 安装 Node.js 22 或更高版本，并重新打开终端。用 `node --version`、`npm --version` 确认命令可用。
2. 解压本地／VPS 项目到普通可写目录，保留目录结构，不在压缩包预览窗口中直接运行。
3. 双击 `启动本地.cmd`。首次会安装依赖、建立 `.env` 并启动服务。
4. 保持窗口打开，查看首次初始化密钥，打开 `http://localhost:3000/setup` 设置站长。
5. 初始化后访问 `http://localhost:3000/` 创建活动，或 `/admin` 管理活动。
6. 停止时在运行窗口按 Ctrl+C。关闭窗口后，网页和定时开奖服务都会停止。

已有 `.env` 时 setup 不应覆盖现有配置；升级请保留自己的文件，不要用 `.env.example` 覆盖。若使用不同端口，以实际端口访问，启动脚本中的 3000 提示只代表默认值。

### 3.2 命令行启动

在项目根目录打开 PowerShell：

```powershell
npm ci --omit=dev
npm run setup
npm start
```

首次运行 `npm run setup` 后可先编辑 `.env` 再启动。例如仅本机使用：

```dotenv
PORT=3000
NODE_ENV=development
DATA_DIR=./data
TRUST_PROXY=0
BASE_URL=
```

修改环境配置后重启服务。`DATA_DIR=./data` 按运行工作目录解析，所以始终在项目根目录启动。不要同时启动两个进程操作同一份数据。

### 3.3 手机与局域网

手机上的 `localhost` 是手机自身，不能填写电脑的 `localhost`。同一局域网演示时，让手机与电脑连接同一网络，在活动“手机访问地址”填写电脑可达地址，例如 `http://192.168.1.50:3000`，并允许 Windows 防火墙的专用网络入站。多网卡、VPN 或虚拟网卡可能让自动识别地址出错，应手动指定。

局域网 HTTP 能用于基础名单与互动测试；微信／钉钉 OAuth、TG webhook、网站账号第三方登录需要公网可访问的 HTTPS 域名与供应商域名配置。只配置局域网 IP 不会让这些平台回调成功。

## 4. VPS Docker 部署与 HTTPS

### 4.1 目录与现有部署约定

项目的 Compose 服务名为 `studio`，容器内部服务端口为 `3000`。对已有用户部署，沿用容器名 `xiazheteng-lucky`、宿主机端口 `3010`，不擅自换卷。交付的基础 `compose.yaml` 可能采用 `127.0.0.1:3000:3000`；请核对并按下面示例把宿主机一侧改为 3010。仅修改外侧端口，内部保持 3000。

先在 VPS 安装 Docker Engine 和 Compose 插件，执行 `docker version`、`docker compose version` 确认。把本地／VPS 项目上传到 `/opt/youtube-giveaway-studio`；下文命令均在该目录运行。

```sh
cd /opt/youtube-giveaway-studio
cp .env.example .env
chmod 600 .env
```

编辑 `.env`：

```dotenv
PORT=3000
NODE_ENV=production
DATA_DIR=/app/data
SETTINGS_ENV_PATH=/app/data/settings.env
TRUST_PROXY=1
BASE_URL=https://lucky.example.com
SIGNIN_BASE_URL=https://lucky.example.com
```

Docker 镜像自带 Node.js，不要求宿主机安装 Node 才能复制示例配置。镜像使用非 root 的 `node` 用户；运行时设置与媒体放在持久卷中。不要将 `DATA_DIR` 改到容器中未挂载的位置。

新部署可采用如下 Compose 结构；已有部署必须先用 `docker inspect xiazheteng-lucky` 核对挂载，保留原卷名称和 Compose 项目名：

```yaml
services:
  studio:
    build: .
    container_name: xiazheteng-lucky
    restart: unless-stopped
    env_file: .env
    ports:
      - "127.0.0.1:3010:3000"
    volumes:
      - studio-data:/app/data
volumes:
  studio-data:
```

```sh
docker compose up -d --build studio
docker compose ps
docker compose logs --tail=100 studio
curl -f http://127.0.0.1:3010/healthz
```

日志可能含首次 setupKey，只在服务器私下查看。首次初始化应在 HTTPS 反代配置完成后进入 `/setup`。

### 4.2 域名、nginx 和 TLS

把域名 A／AAAA 记录指向 VPS。若使用 CDN 代理，先确认源站 HTTPS 正常，不使用“灵活 SSL”造成 HTTPS／HTTP 重定向循环。

nginx 的 HTTP 示例：

```nginx
server {
    listen 80;
    server_name lucky.example.com;
    client_max_body_size 20m;
    location / {
        proxy_pass http://127.0.0.1:3010;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;
    }
}
```

以 Ubuntu／Debian 为例安装 nginx 与证书插件，保存站点后运行：

```sh
sudo nginx -t
sudo systemctl reload nginx
sudo certbot --nginx -d lucky.example.com
sudo certbot renew --dry-run
```

`certbot` 不存在时先按系统官方安装方式安装 `certbot`、`python3-certbot-nginx`。证书申请需要域名解析正确、80／443 可达；云安全组也应放行。证书生成后检查 HTTPS server 中仍有上述代理头和 `client_max_body_size 20m`。

应用只绑定宿主机 127.0.0.1:3010，对外开放 80／443；不要额外公网放行 3010。`TRUST_PROXY=1` 用于一层可信反向代理。存在 CDN 或更多代理层时按真实链路核对，不机械设置成无限信任。`BASE_URL` 必须是用户实际访问的 HTTPS 根地址，否则安全 Cookie、OAuth 和来源校验可能出错。

### 4.3 日常操作

```sh
docker compose logs --tail=100 studio
docker compose restart studio
docker compose stop studio
docker compose up -d --build studio
```

`restart` 不会重新读取修改后的 Compose 环境；变更 `.env` 后应使用 `docker compose up -d --force-recreate studio`。绝不能用 `docker compose down -v` 做普通重启／升级，它会删除数据卷。

## 5. VPS Node.js／systemd 部署

安装 Node.js 22+，进入项目执行 `npm ci --omit=dev`、`npm run setup`，编辑 `.env`，再 `npm start`。此模式 `DATA_DIR=./data`，`SETTINGS_ENV_PATH` 可不指定，`PORT` 可设 3000 或其他空闲端口。nginx 的 `proxy_pass` 应与实际端口一致。

项目提供 `deploy/youtube-giveaway.service`，使用前逐项核对 `User`、`WorkingDirectory`、`ExecStart` 和 Node 可执行文件路径。建议专用无特权用户拥有数据目录，避免 root 运行应用。示例命令：

```sh
sudo cp deploy/youtube-giveaway.service /etc/systemd/system/youtube-giveaway.service
sudo systemctl daemon-reload
sudo systemctl enable --now youtube-giveaway
sudo systemctl status youtube-giveaway
sudo journalctl -u youtube-giveaway -n 100 --no-pager
```

`deploy/install.sh` 适合新服务器，默认使用 `/opt/youtube-giveaway-studio`，遇到已有应用／服务／端口会停止。已有 Docker 或 Node 部署不要再跑安装脚本覆盖目录；直接沿用原运行方式更新。

定时开奖依赖服务持续运行；Windows 休眠、VPS 进程停止期间不能期待准点执行。本地会在下一次启动调度时处理到期任务，但活动也可能先因保留期限到期被清理。

## 6. Cloudflare 独立 Worker 部署

### 6.1 准备资源

使用 Cloudflare 项目，安装 Node.js 22+，运行：

```sh
npm ci
npx wrangler login
```

检查 `wrangler.jsonc`，主要配置如下：

| 配置 | 作用 | 注意事项 |
| --- | --- | --- |
| `name` | Worker 名称，默认 `xia-zhe-teng-giveaway` | 后续绑定应使用实际名称 |
| `main` | `cloudflare/worker.js` | Worker 入口 |
| `assets` | `public/` 和 `ASSETS` | 独立 Worker 模式提供静态页面 |
| `REGISTRY` | `StudioRegistry` Durable Object | 账号、全局配置、活动索引等 |
| `ROOMS` | `DrawRoom` Durable Object | 活动与开奖、揭晓进度等 |
| `migrations` | DO SQLite 类迁移 | 保留原迁移历史，不随意重写 v1 |
| `CONFIG_KV` | KV 命名空间 | 必须是实际 KV 绑定，不是文本变量 |
| `MEDIA` | R2 bucket | 上传音频等媒体 |
| `STUDIO_ID` | 默认 `main` | 站点数据空间标识，升级不要随意改 |

首次创建 KV：

```sh
npx wrangler kv namespace create CONFIG_KV
```

把命令返回的真实 ID 填入 `wrangler.jsonc` 的 `kv_namespaces` 对应项。创建 R2（示例名应与配置一致）：

```sh
npx wrangler r2 bucket create xia-zhe-teng-giveaway-media
```

Cloudflare 账号需要先启用相应产品，R2 可能要求开通计费资料。DO SQLite 可用性、套餐、资源额度与流量费用以账号当时实际条件为准。不要对已经存在的桶／KV 无脑重复创建；先在控制台核对。

### 6.2 设置密钥并发布

```sh
npx wrangler secret put SETUP_KEY
npm run cf:check
npm run cf:deploy
```

也可使用 `npm run deploy:cloudflare`／Windows 双击 `部署到Cloudflare.cmd`；无论入口如何，先完成绑定和 `SETUP_KEY`。`cf:check` 是 dry-run，只检查构建，不等于部署成功。以实际发布返回地址或绑定的自定义域名为准。

在 Worker → Settings → Domains & Routes 添加自定义域名。使用 `https://lucky.example.com/setup` 初始化，之后登录 `/owner` 设置站点登录方式。活动签到的公开域名、YouTube API 等再按本手册配置。

Cloudflare 本地开发可从 `.dev.vars.example` 复制到 `.dev.vars`，填入本地测试用 `SETUP_KEY` 和需要的变量，再 `npm run cf:dev`。本地 Wrangler 存储不等于线上存储；本地测试完成不证明线上密钥／权限／回调已配置正确。`.dev.vars` 必须忽略，不提交仓库。

## 7. Cloudflare Pages + Worker 与 GitHub Actions

### 7.1 架构和官方限制

本方案保留一个独立 Worker。Cloudflare 官方说明：Durable Object 必须由 Worker 创建部署，不能在 Pages 项目内部创建并部署 DO；Pages 可以绑定外部 DO。本项目选择更清晰的服务绑定代理：Pages Functions → `API_BACKEND` → 独立 Worker → `REGISTRY`／`ROOMS`／KV／R2。

官方参考：<https://developers.cloudflare.com/pages/functions/bindings/#durable-objects>、<https://developers.cloudflare.com/pages/functions/bindings/#service-bindings>。

`SETUP_KEY`、平台 Secrets 和 DO／R2／KV 留在 Worker。Pages 只需要 `API_BACKEND` 服务绑定等页面部署配置；不要复制密钥到静态前端。浏览器地址应始终使用同一个 Pages 自定义域名，不能一半页面打开 Worker 域名、一半打开 Pages 域名，否则账号 Cookie、OAuth state 与本地录像存储会分开。

### 7.2 发布顺序

1. 先按上一章发布 Worker、创建真实存储并设置私有 `SETUP_KEY`。
2. 确认 Worker 名称，与 Pages 的 `API_BACKEND.service` 完全一致。
3. 构建 Pages 静态资源，输出目录为 `pages-dist`。这里是复制实际 `public/`，不是生成跳转到另一个网站的首页。
4. 把 Pages Functions 一并部署；采用 Wrangler／Git 集成构建，不用仅上传静态文件的方式遗漏 Functions。
5. 在 Pages 项目 Settings → Bindings（或 Functions → Service bindings，以控制台实际位置为准）添加服务绑定：变量名 `API_BACKEND`，目标为刚发布的 Worker；生产和预览环境分别核对。
6. 配置 Pages 自定义域名，再设置 Worker 中与用户入口有关的 `BASE_URL`、`SIGNIN_BASE_URL` 为 Pages HTTPS 域名。
7. 重新部署 Pages 后，在 Pages 域名检查 `/`、`/account`、`/setup`、`/owner`、`/api/account` 以及媒体和第三方回调。

项目提供的确切命令如下（在 Cloudflare 项目根目录执行）：

```sh
npm ci
npm run pages:build
npm run pages:test
npx wrangler pages project create your-pages-project --production-branch main
npm run pages:deploy -- --project-name your-pages-project
```

`your-pages-project` 替换为实际 Pages 项目名；已有项目不再 create。`pages:build` 会将 `pages-functions` 编译为输出中的 `_worker.js`，并生成 `_routes.json`、`_redirects` 等文件。只上传未构建的 `public/` 会缺少 API 功能。`npm run pages:dev` 用于本地预览，远程服务绑定是否可用取决于本地 Wrangler 资源配置，不能把无后台绑定的预览视为完整线上验收。

`API_BACKEND` 是 Worker 类型 Service Binding，不能填普通字符串 URL。目标 Worker 必须属于可绑定的账号范围。若预览与生产共用同一个后台，则它们也会共用活动与账号数据；正式活动不要在预览分支随意删除数据。若需要隔离，单独部署测试 Worker 与存储并分别绑定。

### 7.3 GitHub Actions 配置

将 Cloudflare 项目内容作为仓库根目录上传，不上传 `.dev.vars`、`.env`、依赖、`.wrangler` 缓存或私有数据。Actions 命令默认从仓库根目录执行；若放在子目录，工作流的 working-directory 必须相应修改。

仓库 Settings → Secrets and variables → Actions 中配置：

| 类型 | 名称 | 内容 |
| --- | --- | --- |
| Secret | `CLOUDFLARE_API_TOKEN` | 限定到目标账号的部署令牌 |
| Secret | `CLOUDFLARE_ACCOUNT_ID` | Cloudflare 账号 ID |
| Secret | `SETUP_KEY` | 首次站长初始化所需私有随机密钥，按工作流注入 Worker |
| Variable | `CF_PAGES_PROJECT` | 已创建的 Cloudflare Pages 项目名，例如 `your-pages-project` |

交付的 Worker 工作流已注入 GitHub Secret `SETUP_KEY`。发布前请在仓库 Secrets 创建该值；手动部署时可在 Cloudflare Worker 控制台创建该 Secret，或执行 `npx wrangler secret put SETUP_KEY`。旧版 `ADMIN_PASSWORD` 不能代替首次站长初始化。

API Token 应允许目标 Worker 脚本发布及所需资源访问，并有 Cloudflare Pages 编辑权限；KV／R2 创建权限只在流程确实自动创建资源时才需要。DO 迁移、账号资源访问权限需要与实际工作流匹配。API Token 不是 Global API Key，也不是 Cloudflare 登录密码。

先运行独立 Worker 工作流，再运行 Cloudflare Pages 工作流。Actions 的绿色成功只代表发布任务结束，还要打开最终 Pages 地址实际登录和检查 API。不要再依赖旧的 `PUBLIC_APP_URL` 跳转站点方案，不用把 GitHub 仓库 Settings → Pages 设为发布目标；目标是 Cloudflare Pages。

## 8. 环境变量与配置优先级

本地使用项目 `.env`；Docker 使用 `.env` 注入，页面保存的运行设置可能写入 `SETTINGS_ENV_PATH`；Cloudflare 使用 Worker 的 vars／Secrets，本地开发使用 `.dev.vars`。环境变量修改后通常需要重启进程／重新部署。私密值使用 Secret，不能写进公共页面配置。

账号／站点设置采用“站长已保存值 > 环境变量 > 程序默认值”；已在后台明确保存的关闭开关也应覆盖环境中的开启值。活动签到历史模块与账号登录模块是两个配置体系；当前 `signin-service.js` 的活动签到配置仍采用“环境变量 > 页面保存值”的历史顺序。因此，若活动签到页面保存后看似不生效，先检查并移除或改正同名签到环境变量；不要把账号模块的新优先级套到签到模块。

### 8.1 基础与站点配置

| 变量 | 默认／建议 | 具体用途 |
| --- | --- | --- |
| `PORT` | `3000` | 本地 Node 内部监听端口；Docker 容器保持 3000 |
| `NODE_ENV` | 本地 development；VPS production | 生产安全 Cookie 等行为 |
| `DATA_DIR` | 本地 `./data`；容器 `/app/data` | 本地数据库、密钥、上传和配置目录 |
| `SETTINGS_ENV_PATH` | 可选；容器 `/app/data/settings.env` | 页面保存的环境式配置持久化位置 |
| `TRUST_PROXY` | 直连 0；单层 nginx 1 | 识别可信代理后的协议／客户端地址 |
| `BASE_URL` | 公网 `https://lucky.example.com` | 站点对外 HTTPS 根地址；不填 `/admin` |
| `SITE_NAME` | 瞎折腾摇奖吧 | 站点名称；后台保存值优先 |
| `SETUP_KEY` | Cloudflare 必填私有 Secret | 第一次创建站长的初始化密钥 |
| `STUDIO_ID` | CF `main` | Cloudflare 站点存储标识 |
| `SCHEDULER_INTERVAL_MS` | 本地默认 1000 | 本地调度检查间隔，程序最小限制 1000ms |
| `YOUTUBE_API_KEY` | 空 | 可选 YouTube Data API v3 密钥 |

本地会话签名密钥由程序在 `DATA_DIR/session-secret` 自动生成，保留该文件，不需要另设旧版 `ADMIN_PASSWORD`。站长密码通过 `/setup` 创建，不能靠填写 `ADMIN_PASSWORD` 代替初始化。

### 8.2 账号开关与临时活动期限

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `ALLOW_PASSWORD_REGISTER` | `true` | 普通用户名密码注册／对应普通入口 |
| `ENABLE_EMAIL_REGISTER` | `false` | 邮箱验证方式，另需真实发送配置 |
| `ENABLE_PHONE_REGISTER` | `false` | 手机验证方式，另需真实发送配置 |
| `ENABLE_WECHAT_LOGIN` | `false` | 站点微信网页扫码登录 |
| `ENABLE_DINGTALK_LOGIN` | `false` | 站点钉钉登录 |
| `ENABLE_TELEGRAM_LOGIN` | `false` | 站点 Telegram Login Widget |
| `UNVERIFIED_ACTIVITY_HOURS` | `24` | 未验证账号新活动的开奖期限 |
| `UNVERIFIED_RETENTION_HOURS` | `24` | 揭晓完成后保留时长 |

使用明确 `true`／`false`，不要写“开启／关闭”。两个小时数均支持 1–168 的整数，非法值回退默认 24。仅打开开关不等于第三方可用；外部方式还需要对应凭证、真实回调域名及平台权限。默认 24 小时是默认配置，改值后应检查前端规则提示与新建活动的实际到期信息。

| `EMAIL_SENDER_URL` | 邮箱验证码 HTTP POST 服务 URL |

| `EMAIL_SENDER_FROM` | 邮件发送源标识，具体意义由网关适配 |
| `PHONE_SENDER_URL` | 手机验证码 HTTP POST 服务 URL |
| `PHONE_SENDER_TOKEN` | 手机发送网关 Bearer Token，敏感值 |
| `PHONE_SENDER_FROM` | 短信发送源标识，具体意义由网关适配 |

本次实现也把 `WECHAT_APP_ID`／`WECHAT_APP_SECRET`、`DINGTALK_CLIENT_ID`／`DINGTALK_CLIENT_SECRET`、`TELEGRAM_BOT_TOKEN`／`TELEGRAM_BOT_USERNAME` 作为账号第三方凭证的环境回退。它们同时是原有活动签到变量，因此**两套配置并非在环境变量名称上完全隔离**。同一个环境中的微信公众号凭证通常不能用于开放平台网站登录；建议在 `/owner` 为账号登录明确保存网站应用凭证，在活动扫码设置中保存对应签到凭证，并分别验收。不要仅因环境中已有活动签到配置就打开网站登录开关。

| `DINGTALK_CLIENT_ID`／`DINGTALK_CLIENT_SECRET` | 活动签到钉钉应用凭证 |

| `TELEGRAM_WEBHOOK_SECRET` | 活动签到 webhook 校验密钥，可由页面生成 |

账号登录建议统一在 `/owner` 填写凭证，具体字段见下一章；不要把活动签到的 `WECHAT_APP_ID` 当成微信开放平台网站应用登录凭证。

## 9. 账号、验证服务与第三方登录

### 9.1 站长后台所有账号字段

`/owner` 中可设置：用户名密码、邮箱验证码注册、手机验证码注册、微信、钉钉、Telegram 六类开关；邮箱服务 URL／Token；手机服务 URL／Token；微信 AppID／AppSecret；钉钉 Client ID／Client Secret；Telegram Bot 用户名／Bot Token。用户列表可查看用户名、角色、验证状态与注册时间，点击刷新重新读取。

凭证保存后不回显，密码框留空表示保留原密钥，不表示清空。后台显示“已配置”只说明所需字段存在，不表示供应商已经验收。变更后用一个退出登录的浏览器或无痕窗口检查普通用户实际看到的入口。确认能用其他方式登录之前，不要关闭自己唯一可用的用户登录方式；站长保留专用密码入口。

### 9.2 邮箱／手机发送服务

本项目配置的是 HTTP 发送网关，不是直接填写 SMTP 主机或短信供应商签名。若供应商 API 格式不同，需要自己的服务端适配器接收此契约并调用实际发送平台。

程序向配置 URL 发送 HTTP POST，`Content-Type: application/json`；设置了 Token 时附带：

```http
Authorization: Bearer <服务Token>
```

核心 JSON 字段：

```json
{
  "type": "email",
  "destination": "person@example.com",
  "code": "123456",
  "from": ""
}
```

手机号时 `type` 为 `phone`，`destination` 为手机号，建议带国家区号，例如 `+8613800000000`（示意号码，不用于实际发送）。Cloudflare 路径还可能提供同义 `to` 和 `expiresIn: 600`，适配器应以 `destination`／`code`／`type` 为基本契约，忽略无关附加字段。

发送服务只有在真实接受并完成规定的发送流程后返回 2xx JSON：

```json
{"success": true}
```

返回空白、HTML、`{"ok":true}`、字符串 `"true"`、HTTP 错误或仅模拟成功，都不能视为验证码已发送。程序约 10 秒发送超时，并拒绝服务跳转；建议使用直接 HTTPS 端点。不要把验证码写入用户可公开访问的日志或接口。需要在邮箱／短信供应商处配置真实发件域、发件地址、模板、签名、额度和收件限制，这些不是勾选开关就自动开通。

验证码约 10 分钟有效，限制频繁发送和错误尝试，一次使用；发送后在原浏览器完成注册／绑定，不要切换浏览器丢失会话。邮箱／手机注册仍填写站点用户名和密码。登录后可在“绑定”区域验证现有账号；已经绑定其他账号的地址不能重复绑定。此版本不应被当成提供了未见于页面的“找回密码”或短信一键登录功能。

### 9.3 网站账号第三方登录

| 方式 | 平台要求 | 本站回调 |
| --- | --- | --- |
| 微信 | 微信开放平台网站应用、网站扫码登录权限、已审核域名，`snsapi_login` | `https://lucky.example.com/api/account/oauth/wechat/callback` |
| 钉钉 | 应用登录权限、可使用范围、个人资料读取权限、正确重定向 URL | `https://lucky.example.com/api/account/oauth/dingtalk/callback` |
| Telegram | @BotFather 建机器人并设置网站登录域名，官方 Login Widget | `https://lucky.example.com/api/account/oauth/telegram/callback` |

微信开放平台网站登录与公众号网页授权是不同产品，不可互换 AppID／Secret。钉钉回调应配置完整 HTTPS 地址，账户需在应用可用范围内。Telegram 使用 Login Widget 的签名数据，不是 Mini App `initData`，也不是签到机器人的 `/start` 链接。填写机器人用户名时采用 `your_login_bot`，按页面规范去掉 `@`。

外部授权从 `/account` 提供的按钮发起，程序会绑定浏览器会话并校验一次性 state。不要手工拼带 `code` 的 callback 地址测试登录。重复使用已消费授权、超过有效时间、跨浏览器回调，都会被拒绝。无真实第三方凭证时只能验证配置和协议路径，不能声称生产扫码登录已验收。

## 10. 活动创建、导入和筛选

### 10.1 完整创建流程

1. 打开 `/`，先填写表单也可以；提交创建时需要登录，浏览器草稿用于减少登录往返丢失内容。
2. 选择参与方式：从视频、从 blog、自定义名单、微信／钉钉／TG 扫码。
3. 填写活动名称、中奖人数、手动／自动模式、最高虚晃次数，以及对应来源信息。
4. 配置筛选、倒计时和舞台，创建活动。
5. 在活动卡片导入／抓取名单，检查“查看参与名单”中的合格人数。
6. 打开大屏、检查音乐和二维码，确认后开始抽奖。

### 10.2 创建与筛选字段

| 字段 | 含义与建议 |
| --- | --- |
| 参与方式 | 决定名单来源，不同方式不是同一份自动同步名单 |
| 视频／文章链接 | 填实际完整 URL；其他平台是否支持以实际导入结果为准 |
| 扫码平台 | 微信、钉钉、TG；只选择已完成配置的平台 |
| 活动名称 | 管理列表和大屏标题，服务端最长 200 字符 |
| 中奖人数 | 1–100，不能假定超过合格人数还能产生足量中奖者 |
| 抽奖模式 | 手动逐位／自动连续，默认手动 |
| 最高虚晃次数 | 0–100，默认 8；0 直接揭晓。候选画面不改变真实中奖者 |
| 参与关键词 | 评论需包含该文本；不区分大小写，非正则表达式 |
| 最终公示文案 | 开奖完成的说明文案 |
| 排除视频作者 | 依赖已读到真实视频作者频道 ID |
| 相同参与者仅一次 | 默认去重，按参与者 ID 判断，不能只看显示昵称 |
| 屏蔽频道 ID | 逗号分隔，匹配真实 ID，而不是随意填频道昵称 |
| 限定频道 ID | 非空时只允许列表中的参与者 |
| 评论开始／结束时间 | 按评论发布时间过滤；手工名单没有时间的行不能假定受此限制 |
| 倒计时结束时间 | 启用倒计时时必须填写有效时间 |
| 启用倒计时开奖 | 到点由服务端调度；勾选后界面通常选择自动，也可再改手动 |

名单抓取成功数量与筛选后合格数量不同。关键词、作者排除、黑白名单、时间范围、去重会共同影响抽奖池；开奖前一定核对合格名单。

### 10.3 视频和文章导入

YouTube API 可选；无 API 时尝试公开评论，稳定性受网站限制、网络、视频状态影响。配置官方 API：Google Cloud Console 创建项目 → API 和服务 → 库 → 启用 YouTube Data API v3 → 凭据创建 API Key → 将 API 限制为 YouTube Data API v3 → 在站长“API 与扫码平台设置”保存。注意配额、服务端出口网络与密钥限制适配，不能用不匹配的浏览器来源限制阻断服务端请求。

API 无法读取已删除、私密、关闭或不可见的评论；其他视频网站／blog 不保证支持。无法直接抓取时，把自己合法取得的评论整理成名单上传。文章正文不等于评论，不能把正文抓取成功当成评论参与者已导入。

### 10.4 名单文件夹

下载 `名单导入模板.zip`，解压后编辑一份 XLSX／CSV／TSV 表，把头像放入同一文件夹或子文件夹，再拖入整个文件夹。

| 列名 | 说明 |
| --- | --- |
| 编号 | 稳定唯一编号；重复编号会去重 |
| 姓名 | 自定义名单展示名称 |
| 头像文件 | 含扩展名，例如 `001.jpg`，须与文件名完全对应，可空 |
| 账号 | 评论类名单的真实 `@账号` |
| 评论 | 评论类完整正文 |
| 获奖名称 | 可选，从最高奖到最低奖顺序填写，不与所在行人员绑定 |

示例：

```csv
编号,姓名,头像文件,获奖名称
001,小林,001.jpg,特等奖
002,小陈,002.jpg,一等奖
003,小周,,二等奖
```

上例仅定义三个奖项名称，不指定小林／小陈／小周中奖。不要用这一列“安排中奖人”。

限制：一份名单不超过 8MB，每次 1–10000 行；头像 PNG／JPG／WebP 单张不超过 300KB，总量不超过 10MB；目录内保留一份名单表，避免重复文件与同名头像。CSV 建议 UTF-8，第一行为表头。评论类导入需要真实 `@账号` 与评论列，姓名不能替代账号。开奖后不能再改名单。

### 10.5 活动卡片操作

待开奖可抓取评论、导入名单文件夹、查看签到二维码、开始抽奖、应用当前舞台设置、编辑活动、查看合格参与名单、打开大屏、删除。编辑活动对话框主要修改名称和关键词，不能假定它会重建整个活动。舞台表单的修改需点击对应活动“应用当前舞台设置”，不会自动修改所有旧活动。

已开奖可继续手动揭晓下一位、下载完整 Excel／CSV、图片与视频导出。删除不可撤销，会清理相关记录，先下载所需结果。表格下载需要有效管理登录，不能只转发接口地址给无权限访客。

### 11.1 舞台全部主要字段

### 11.3 音乐

站长“音乐设置”中可切换可用音乐／全部曲目／音乐推荐，搜索曲名、作者或别名；分别选择候场、摇奖、中奖颁奖曲目，调音量，试听后保存。默认候场《喜洋洋》、摇奖《Go Time》、颁奖《Victory》，具体曲库与授权参见 `精选音乐曲库.md`、`MUSIC-LICENSE.md`。

可一次选择多首 MP3／WAV／OGG／M4A／WebM，单首最大 12MB；上传后分配播放阶段并保存。曲库记录不代表都有音频，未绑定可播放文件的曲目不能作为实际背景音乐。无损文件过大时先转换为合适码率 MP3／M4A。

浏览器限制自动播放，大屏需要点击“开启音乐”。确认没有静音、浏览器标签静音或系统音量问题。画面可运行但音乐不响，不代表服务端故障。自有音乐的播放／直播／导出授权由使用者确认。

### 11.4 观众签到配置

在站长 API／扫码平台设置中配置，与 `/owner` 的网站账号登录分开。公共字段是“活动公开域名”，填用户实际访问的 HTTPS 根地址。保存 Secret 留空保留原值。

| 平台 | 填写字段 | 平台侧具体设置 | 本站回调 |
| --- | --- | --- | --- |
| 微信公众号 | AppID、AppSecret、可选 MP_verify 文件 | 公众号有网页授权权限；配置网页授权域名；按要求完成域名验证 | `/api/wechat/callback` |
| 钉钉 | Client ID／AppKey、Client Secret／AppSecret | 配置应用登录回调、个人信息权限与用户可用范围 | `/api/signin/dingtalk/callback` |
| Telegram | Bot Token、Bot 用户名 | @BotFather 建机器人；公开 HTTPS webhook；保存后启用接收 | `/api/signin/telegram/webhook` |

微信上传必须是平台给出的 `MP_verify_*.txt`，保留文件名与原内容；不要拿截图代替。验证文件访问路径在站点根目录。Pages 架构也要保证该动态验证路径转交 Worker，而不是落入静态 404。

TG 点击“保存并启用 TG 接收”后会识别机器人、注册 webhook 并保存启用状态。只填 Token 不等于 webhook 已启用；改域名／Token 后应重新启用。观众扫码进入机器人后点击开始签到，通过机器人返回按钮进入互动页面；重复签到不会增加抽奖机会。

活动签到不会自动创建网站管理账号，也不会给观众开放 `/admin`。反过来，网站登录成功也不代表已报名某场活动。请用活动二维码走完整手机签到链路测试。

### 11.5 互动二维码

自定义名单和评论活动的二维码可以用于手机互动；扫码类活动通过所选平台完成身份确认并加入名单。复制管理页面生成的完整链接，不自行删除 `id`／`token`。活动令牌可让持有人访问相应分享内容，应只在需要的范围公开。

手机不能打开时先检查域名／IP、同一网络、防火墙、TLS 与平台内置浏览器，不要先修改中奖逻辑。Pages 域名和 Worker 域名混用时还要检查 Cookie 与 callback 来源。

## 12. 开奖、大屏与导出

### 12.1 开奖与手动揭晓

开奖前检查名单、合格人数、中奖人数、筛选条件、动画、最高虚晃、奖项、音乐、倒计时和二维码。服务端确定中奖名单，画面候选／虚晃只是表现，不重新抽签。

默认手动模式开始后揭晓一位并等待；当前名次动画完成后才可点击“立即抽取下一位”。不能跳过尚未完成的名次；多个管理页面同时点下一位时，旧进度请求可能被拒绝，应刷新而不是连点。自动模式连续完成全部名次，通常按名次倒序揭晓。

倒计时自动触发第一位；若选择手动模式，后续仍需逐位点击。刷新保留服务端进度，不能把刷新当成重新抽奖。已开奖活动不能修改名单／舞台；需要新的抽奖请新建活动。

### 12.2 大屏与 OBS

从活动卡片“直播大屏”打开。默认画布面向 16:9，支持 4K 尺寸输出并按窗口缩放。右上角提供音乐、全屏和有权限时的开奖控制。打开公开分享大屏的访客不会仅凭分享令牌获得管理权限。

OBS 使用浏览器来源粘贴完整大屏链接，宽高可设 3840×2160 或实际直播分辨率。浏览器来源与日常浏览器属于不同会话／存储，不能假定 OBS 中自动拥有站长登录或能在 Chrome 导出 OBS 内部录像。使用 OBS 本身录制时，按 OBS 音频输出设置检查音轨。

### 12.3 表格和图片

完整中奖 Excel 包含名次、账号、自定义姓名、完整评论、获奖名称与完整导入信息；CSV 方便其他系统处理。大屏中的长评论可能省略，导出表格用于保存完整内容。

导出页可选 720p（1280×720）、1080p（1920×1080）、2K（2560×1440）、4K（3840×2160），长名单可上一页／下一页逐页导出 PNG。“导出本页 PNG”只导当前页，不能认为一张图包含所有分页结果。

### 12.4 动画回放与真实现场录像

这两种视频来源不同：

| 项目 | 开奖动画回放 | 完整现场视频 |
| --- | --- | --- |
| 内容来源 | 根据已保存开奖结果重新绘制 | 本浏览器实际打开大屏时录到的内容 |
| 候场与手动等待 | 不包含真实长时间等待 | 包含实际录到的候场、开奖、后场 |
| 分辨率／FPS | 使用导出页选择，30／60 FPS | 使用现场录制的原始尺寸和实际帧率 |
| 音乐 | 可选包含当前所选音乐 | 实际现场录到的音乐 |
| 未曾录到的历史 | 可以重放动画 | 无法补回 |

现场录制在支持的 Chrome／Edge 大屏页面启动，查看“现场录制中”状态。录像片段保存在录制大屏所属浏览器、用户资料和同源网站的 IndexedDB，不上传到服务器。域名、HTTP／HTTPS、浏览器或浏览器用户资料不同，就不是同一份本地录像存储。

正确操作：同一浏览器打开大屏 → 确认录制状态和音乐 → 完成开奖 → 继续保留大屏记录后场 → 结束后到同源导出页“刷新录像” → 选录像及完整／自定义开奖前保留分钟数 → 导出。导出会结束该份现场录制，之后发生的后场不会进入该文件。也可先在大屏点“结束并保存”，再导出。

“自定义开奖前保留时间”只裁掉多余前场，保留全部开奖与已录后场；必须录到开奖时间才能按开奖点裁剪。裁剪需要实时处理，不是即时服务器转码。

视频为 WebM，导出按实时速度执行。保持页面前台，禁用休眠／后台节能，确认本地磁盘与浏览器配额。4K／60 FPS 消耗较大，实际帧率由设备性能决定。可取消任务后降低规格重试。清除网站数据、无痕窗口关闭或浏览器存储清理会使尚未下载的现场录像丢失。

## 13. 数据、备份、升级与回滚

### 13.1 本地／Node 数据

备份应包含 `.env`、整个 `DATA_DIR`、自定义运行配置、原始名单／头像／音乐以及需要留存的导出结果。数据目录包含 `giveaway.sqlite`、会话密钥、账号与平台相关持久配置和媒体。不要只备份数据库忽略音乐和设置。

停止服务后备份，避免 sql.js 正在写文件导致不一致。`deploy/backup.sh` 只复制默认位置的 SQLite 并按周期删除旧副本，不能代替完整备份，也不自动覆盖你改过的数据路径。离线备份应设访问权限，不能放入公开仓库或网站静态目录。

### 13.2 Docker 完整备份

先确认真正挂载的卷名：

```sh
docker inspect xiazheteng-lucky --format '{{json .Mounts}}'
```

下面 `实际数据卷名` 必须替换为 inspect 显示的名称，不要直接猜 `studio-data`；Compose 常自动加目录前缀。示例：

```sh
mkdir -p backups
chmod 700 backups
cp .env backups/env.private
chmod 600 backups/env.private
docker compose stop studio
docker run --rm -v 实际数据卷名:/data:ro -v "$PWD/backups:/backup" alpine:3.21 tar -czf /backup/studio-data.tar.gz -C /data .
docker compose start studio
```

不要连续覆盖唯一一份旧备份，实际运维应使用带时间标识的目录或文件名，并保留离机副本。恢复必须在应用停机时进行，先备份当前卷，再将备份解压至原卷，并核对所有者／写权限。清空或覆盖现有卷属于恢复操作，不在运行中尝试。

### 13.3 升级

1. 下载／导出重要结果和浏览器现场录像。
2. 备份 `.env`、完整数据目录／卷、当前程序版本与配置。
3. 停止旧应用，替换程序文件；保留数据、私密配置、实际 Compose 端口／卷设置。
4. Node 部署执行 `npm ci --omit=dev`；Docker 执行 `docker compose up -d --build studio`。
5. 检查日志和 `/healthz`，登录站长，核对旧活动、名单、音乐、主题、平台设置。
6. 建一场小型测试活动，验证权限、导入、开奖和导出后再继续正式活动。

不要对旧卷运行 `down -v`，不要把新示例覆盖现有 `.env`，不要把前后端发成不兼容版本。多用户升级后旧的免登录管理路径不再等于授权。

### 13.4 回滚

程序回滚需同时考虑数据库结构。若新版本已改变数据，直接换旧镜像不一定兼容。停机后保留当前数据副本，恢复升级前程序／镜像、配置与同一时刻的数据备份，再启动验证。不要把旧备份直接覆盖仍运行的数据库。

### 13.5 Cloudflare 数据和回滚

保留 Worker 名、`STUDIO_ID`、DO 类名与迁移历史、KV namespace ID、R2 桶及绑定。重新 deploy 不等于删除数据；改名或换资源则可能进入空的新空间。

DO／KV／R2 不会自动迁移到本地 SQLite，反之亦然。中奖 Excel／CSV 是结果存档，不是能一键恢复全部账号与进度的完整数据库备份。生产使用应结合 Cloudflare 可用的存储导出／恢复能力和自身恢复流程管理，勿在没有导出功能时声称系统内已有“一键完整备份”。

代码可用 Cloudflare 版本回滚或重新发布已知版本；Pages 可切回成功部署。若回滚涉及 DO 存储结构，仍要确认旧代码兼容当前数据。Pages 与 Worker 有接口依赖，必要时一起回到匹配版本。

浏览器现场录像独立于所有服务端备份，换服务器和恢复卷都找不回没有下载的浏览器录像。

## 14. 验收与故障排查

### 14.1 发布后验收

- `/` 可打开，未登录提交创建被引导到账号入口。
- `/setup` 需要正确私有密钥；首次创建站长后不能再次设置。
- `/owner` 只允许站长；普通用户不能读平台密钥和用户列表。
- 注册两个普通用户，各自只看到自己的活动，更换编号不能越权修改／导出。
- 创建自定义名单测试活动，导入 3–5 人，检查合格名单，手动／自动分别试一次。
- 大屏二维码使用手机实际打开；有平台凭证时走真实供应商回调。
- Chrome／Edge 大屏确认录制后，完成候场／开奖／后场，实际导出 WebM 并播放检查音画。
- PNG、Excel、CSV 下载正常，表格完整评论与奖项正确。
- VPS 重建容器／CF 重新发布后，旧账号、活动、媒体、主题、配置仍在。
- 以测试数据核对到期规则，正式活动结束前主动下载结果。

这些是部署者需要完成的验收动作，不代表本手册写成时已完成真实外部服务验收。没有实际邮箱／短信网关凭证、微信／钉钉应用和 Telegram 机器人授权时，不能宣称第三方全链路已验证。

### 14.2 常见问题

| 现象 | 优先检查 |
| --- | --- |
| Windows 一闪而过／node 不存在 | 安装 Node 22+；重新开终端；在项目目录运行命令查看报错 |
| npm 安装失败 | npm 网络／代理、锁文件、磁盘权限；保留真实错误，不用随意删除 lockfile 碰运气 |
| EADDRINUSE | 是否重复启动；Docker 端口／Node 端口是否冲突，改 PORT 后更新访问地址 |
| Docker 健康但外网打不开 | nginx、80／443 安全组、域名解析、TLS、代理端口是 3010 还是 3000 |
| 413 上传过大 | nginx 的 20m 上限、文件实际限制、总头像和表格大小；不要无限调高掩盖坏文件 |
| 登录后立刻又要求登录 | Cookie 被禁、反代协议／Host 错、BASE_URL 不匹配、切换域名或重启导致会话失效 |
| CSRF／来源校验失败 | 同源访问、不要混用 Worker 和 Pages 域名；检查 nginx Host 与 X-Forwarded-Proto；刷新后重试 |
| 提示请先初始化 | 私有 SETUP_KEY、/setup、原数据卷是否正确挂载；不要新建卷绕过 |
| Cloudflare 缺少 KV／R2／DO binding | 检查真实资源 ID、绑定类型、Worker 迁移，不能用普通变量替代绑定 |
| Pages 页面正常但 API 503／404 | Functions 是否发布、API_BACKEND 是否为 Service Binding、目标 Worker 名、生产／预览绑定 |
| Pages /account 或 /owner 404 | Pages 静态构建的路由别名与 Functions 路由文件是否齐全，重新构建发布 |
| MP_verify 文件／媒体在 Pages 404 | 动态资源代理路由是否覆盖验证文件／媒体，Worker 中对应数据是否存在 |
| OAuth state 无效 | 必须从本站登录按钮开始；同浏览器返回；别跨域、重放或等过期 |
| 第三方按钮不显示 | 开关、完整凭证、域名、供应商权限是否同时具备；站长保存的关闭值会覆盖 env |
| 验证码显示发送失败 | 真实服务 URL／Bearer token、10 秒超时、2xx JSON success:true、供应商配额／模板 |
| 验证码没收到 | 查供应商真实投递状态、垃圾箱、号码国家码；不能将网关假响应当投递成功 |
| TG 没有签到 | webhook 是否启用、HTTPS 可达、Token／用户名、webhook secret、机器人 /start 参数 |
| 评论导入失败／空 | 官方 API 配额、评论权限、出口网络、平台限制；可改名单导入 |
| 导入人数与合格人数不同 | 重复编号、真实账号格式、关键词／黑白名单／时间／作者排除 |
| 开奖人数不足 | 合格池数量，不是原始导入数；开奖前核对 |
| 点下一位无效 | 当前动画未完、已全部揭晓、自动模式或进度已变化；刷新管理页 |
| 定时没执行 | 本地服务停机／休眠、时间配置、名单为空、活动已到期；查 last_error 与日志 |
| 没有音乐 | 点击开启音乐、浏览器自动播放限制、曲目文件、系统和标签音量 |
| 找不到现场录像 | 同浏览器／资料／域名，录制状态、IndexedDB 空间；OBS 存储与普通浏览器不同 |
| 录像卡顿／黑屏 | 保持前台、降低到 1080p／30 FPS、检查设备性能和存储配额 |
| 升级后数据全空 | DATA_DIR、Compose 项目名前缀、真实卷、Worker 名／STUDIO_ID／绑定是否改了 |

### 中奖音效与自动展示停留（本次更新）

每位中奖者确认时播放约1.87秒的用户提供“哇哦～”人声音效。先在大屏点击“开启音乐”；系统遵守浏览器手势限制，静音后音效同步关闭。即使颁奖背景音乐选择静音，开启音乐时仍有中奖提示音。每位中奖者仅播放一次，轮询、最终名单和重复帧不重播。现场完整录像及勾选音乐的动画回放会录入音效。自动模式中奖确认后停留4.5秒，再继续下一位；手动模式2秒，未中奖提示仍为2秒加独立落选2秒。更新必须同时包含public/stage.js、draw-timeline.js、overlay.js、export.js、winner-sound.js；Node/VPS后端导入共享时间线，更新后需重启服务；Pages应重新构建。


当前摇奖效果仅保留“聚焦锁定”（默认）和“随机上浮”。旧活动保存的滚带或狙击效果自动按聚焦锁定显示，中奖结果保持不变。


### 大屏比例自适应与精简效果

抽奖大屏支持16:9、16:10、4:3、21:9、32:9、9:16和手机窗口。舞台等比完整显示，余区使用主题背景；不会裁切内容或把头像拉伸。控制按钮独立占位。竖屏也完整显示横版舞台，小屏文字可能较小，建议横屏。现场录像维持3840×2160，导出原有分辨率选项保留。摇奖效果仅有聚焦锁定（默认）与随机上浮，旧滚带/狙击设置自动回退聚焦锁定。
